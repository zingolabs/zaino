# Integration and test plan

What Zaino must be tested against, and how, drawn from the whole ecosystem: lightwalletd (the wire
contract and its darkside reorg harness), Zebra and zcashd (RPC, reorgs, p2p, consensus rules),
the wallets that call Zaino (librustzcash, zingolib, the ZODL Android and Swift SDKs), the ZODL
cross-implementation suite (`zcash/integration-tests`), and the specs and test vectors (ZIPs,
`zcash-test-vectors`). Research of 2026-10-06; sources are cited per row.

The chain-following engine's own unit, model and simulation tests live beside its crates; this
document covers what sits around and above it.

## 1. Tiers

| Tier                   | Runs                                         | What it proves                                                       | Where                                                    |
| ---------------------- | -------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| T1 unit + golden       | every `cargo test`                           | each named encoder, decoder and rule against fixed bytes and vectors | crate tests                                              |
| T2 models + simulation | every `cargo test`; heavy loop after changes | each core's `check()` invariants under random histories              | crate tests                                              |
| T3 wire conformance    | CI, regtest cluster                          | every RPC answers as the contract says, against oracles (§2)         | `live-tests/clientless`                                  |
| T4 chain shapes        | CI, regtest cluster                          | reorgs, restarts, partitions and upgrades, as wallets see them       | `live-tests/non-finalized-state`, new `live-tests/chain` |
| T5 wallets             | CI, regtest + testnet                        | real wallets sync, receive, send and recover through Zaino           | `live-tests/e2e`, SDK harnesses                          |
| T6 networks            | nightly / pre-release                        | mainnet and testnet sync, NU boundaries, peers, soak                 | `live-tests/sync`, soak                                  |
| T7 ecosystem           | on PRs (dispatched)                          | the ZODL suite and zallet keep working                               | `zcash/integration-tests`                                |

## 5. Where Zaino differs from lightwalletd on purpose

| Behaviour                                      | lightwalletd                                       | Zaino                                 |
| ---------------------------------------------- | -------------------------------------------------- | ------------------------------------- |
| `GetTreeState` at a height with no tree change | walks back, answers an earlier height              | the exact height (clients require it) |
| `GetMempoolStream`, first call after start     | empty, closes at once                              | the mempool at the block              |
| mempool `CompactTx.vin`                        | dropped for every mempool tx (treated as coinbase) | present when TRANSPARENT is requested |
| `CompactTx.fee`                                | never set                                          | set when known (boundaries.md §5)     |
| backend failure on balance/UTXO                | OK with zero (bug #606)                            | non-OK status                         |
| `GetSubtreeRoots`, unsupported pool            | `INVALID_ARGUMENT`                                 | `UNIMPLEMENTED` (non-Sapling)         |

## 6. Chain shapes (T4)

Each shape asserts, on the new branch: prevHash continuity of every stream, block hashes = the
validator's, tx heights and indexes, `chainMetadata` tree sizes, `GetTreeState`, `GetTransaction`
heights, and that `GetLatestBlock`, `GetTreeState` and `GetBlockRange` agree immediately after.
Staged with `invalidateblock` + `generate` on regtest (Zebra's technique; `generate` randomises the
coinbase so forks differ), shapes taken from the darkside datasets and SDK suites.

| ID  | Shape                                                                            | Source                                                   |
| --- | -------------------------------------------------------------------------------- | -------------------------------------------------------- |
| S1  | shallow reorg (depth 6)                                                          | darkside basic-reorg small                               |
| S2  | deep reorg (depth 21; and the deepest the window allows)                         | basic-reorg large; non-finalized-state C9                |
| S3  | same length + 1                                                                  | Swift `testReOrgChangesInboundTxMinedHeight`             |
| S4  | same-height tip replacement, no new block                                        | lwd #204                                                 |
| S5  | tip retreat (blocks vanish)                                                      | lwd #200 (open there), Z#1577                            |
| S6  | tx moves higher                                                                  | tx-height-reorg; Swift; zingolib                         |
| S7  | tx index swap within a height                                                    | tx-index-reorg (reorg height = 663,196 exactly)          |
| S8  | tx removed                                                                       | tx-remove-reorg                                          |
| S9  | outbound tx reorged out, then re-mined / expires                                 | Swift `_testReOrgChangesOutboundTxMinedHeight`, zingolib |
| S10 | reorg while Zaino is down; restart                                               | GHSA-pwwg; C13                                           |
| S11 | reorg during open `GetBlockRange`, `GetTaddressTransactions`, `GetMempoolStream` | GHSA-m7j5, lwd #619, C14                                 |
| S12 | reorg below the final boundary while down → halts                                | C10                                                      |
| S13 | equal-work race (first received wins)                                            | Zebra zcashd-compat `equal_work_race`                    |
| S14 | reorg storm during catch-up                                                      | C17                                                      |
| S15 | reorg across an NU activation                                                    | C16                                                      |
| S16 | index ahead of a syncing validator at start                                      | lwd #360                                                 |

Every S row also asserts the darkside failures that sank zingolib's suite: after the reorg, each `GetBlockRange` block's `prevHash` = its predecessor's hash on the new branch (no stale/new mix), and every `GetTreeState` carries the real 32-byte hash of that branch.

| ID  | Risk                                                                                                                                                                                                   | Fix                                                                                                                                                                                                                                                             |
